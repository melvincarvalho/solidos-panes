SolidOS [[SOLIDOS]] is a data browser for Solid pods. It shows any resource on a pod through panes: small, self-contained views that each know how to display one kind of thing. This document describes how SolidOS is put together, what a pane is, how SolidOS decides which pane to show, how panes are registered, and how a pane creates new things. It is written down from the running code, with Sharon Stratsianis's notes on writing a pane as the guide in the last section.

This is version 0.0.1, dated 9 November 2026; its status line and copyright notice were revised on 13 November 2026. , added the same day, is a proposal and does not describe current behaviour. It documents SolidOS as released at the end of September 2026: mashlib 3.0, solid-panes 5.0, pane-registry 5.0, solid-ui 5.0 and solid-logic 6.0. Where this document and the code disagree, the code is right and this document has a bug; please file an issue in this document's repository.

The document was written after the SolidOS team meeting of 4 November 2026 [[SOLIDOS-MINUTES-2026-11-04]], where the question of a written pane interface came up. It is not adopted by the SolidOS team.

Introduction

A Solid pod holds a person's data as web resources: RDF documents, folders (containers), images, PDFs, anything with a URL [[SOLID-PROTOCOL]]. SolidOS is the application that lets a person browse and edit those resources without a separate app for each kind of data. Point it at a URL and it shows the thing at that URL in the most suitable view it has.

The views are called panes. A pane for address books shows an address book; a pane for chats shows a chat; a pane for folders shows a file listing; a pane for RDF source shows the triples. The stock build registers 36 of them. When several panes could show the same resource, SolidOS shows one and offers the others as tabs.

This document has two audiences: someone who wants to understand what SolidOS does when it opens a URL, and someone who wants to write a pane. to are the description. is the practical guide.

Terminology

subject
The RDF resource being displayed, identified by a URL and represented in code as an rdflib NamedNode [[RDFLIB]]. A subject may be a document, a thing inside a document (a URL with a fragment), or a container.
store
The in-memory RDF graph that SolidOS loads documents into and writes changes through. There is one store per page, shared by all panes.
pane
A JavaScript object that can say whether it applies to a subject and, if so, render it. Defined in .
pane registry
The ordered list of panes known to the page, with lookup by name. Provided by the pane-registry package [[PANE-REGISTRY]].
outliner
The part of SolidOS that takes a subject, asks the registry which panes apply, and places the chosen pane on the page. Lives in solid-panes/src/outline/.
context
The object handed to pane calls, carrying the document, the session and the store. Defined in .
workspace
A container on the pod, named in the user's preferences file, under which a pane creates new things. See .

How SolidOS is put together

SolidOS is a set of npm packages assembled into one browser bundle. Reading from the bottom up:

PackageRole
rdflib [[RDFLIB]]The RDF store, the fetcher that loads documents into it, and the updater that writes changes back.
solid-logic [[SOLID-LOGIC]]Authentication, the shared store instance, and logic that is not UI: profiles, type indexes, containers, access control helpers.
solid-ui [[SOLID-UI]]Widgets and web components panes build from: forms, tables, login, the sharing dialog, the create ("Add") bar, styles.
pane-registry [[PANE-REGISTRY]]The PaneDefinition type and the registry: register, list, byName.
solid-panes [[SOLID-PANES]]Most of the panes, the outliner that places them, and registerPanes.js, the ordered list that registers them. Some panes live in their own packages and are pulled in here: profile, contacts, chat, folder, issue, meeting, source and activity streams.
mashlib [[MASHLIB]]The bundle a pod serves as its data browser: solid-panes plus the page chrome, shipped as databrowser.html. A server that serves it for its resources shows SolidOS for every one of them.

Opening a URL goes like this. Importing solid-panes registers the panes (its entry point calls registerPanes at module evaluation) and creates the outliner for the document. mashlib then takes the subject from the page URL and asks the outliner to show it. The outliner makes sure the subject's document is in the store, loading it if needed, asks the registered panes whether they apply, picks one, calls its render, and puts the returned element on the page under a row of tabs for the other applicable panes.

The pane

A pane is a JavaScript object of the type PaneDefinition [[PANE-REGISTRY]]. The type has four non-optional members, name, icon, label and render; the registry itself checks only for name and label. The rest are optional.

The four members

name: string
A short identifier used by byName and in log output. Examples: "contacts", "folder", "source". The registry indexes a pane under its name only if that name is not already taken; nothing enforces uniqueness.
icon: string
The URL of an icon image, shown on the pane's tab. The type says string; one shipped pane (the human-readable pane) supplies a function of (subject, context) instead, and the tab component accepts that. The tab component also overrides the icon for the profile and social panes.
label(subject, context): string | null

Decides whether the pane applies to the subject, and names it if so. A truthy return value means the pane applies and the string is used as the tab label and tooltip; null, an empty string or undefined mean it does not (the outliner tests truthiness).

The outliner calls label synchronously on every registered pane for every subject shown, and the tab component calls it again per tab, so it should be cheap. An asynchronous label returns a Promise, which is truthy, so the pane would be offered for everything. Shipped labels decide from the store, most often from the subject's rdf:type, and some from the document's content type or from how many statements the store holds about the subject.

render(subject, context, options?): HTMLElement

Builds the view. The outliner expects one element back, which it inserts into the page and tags with a class; a render that returns nothing breaks that step. Shipped panes create the element from context.dom; one older view uses the global document. Reads and writes go through the store, so that changes reach the pod and other panes see them.

The outliner always passes an options object, possibly empty; a few older internal callers omit it. Options are per call: a pane keeps its state in its components or in the RDF, not in options. One shipped view, the trusted-applications view, is called with a null subject by the preferences pane.

Optional members

global: boolean
A pane that is about the session rather than any subject. Set on the home pane and the trusted-applications view. Global panes are never offered as tabs for a subject.
audience: NamedNode[]
Roles the user must have for the pane to be offered. A role is an rdf:type of the user in their preferences file; a pane passes only if the user has every role it lists. solid:Developer gates the default, N3, RDF/XML and data-content panes; solid:PowerUser gates about a dozen, including chat and meetings. See .
shouldGetFocus(subject): boolean
Lets a pane claim the first tab even when it is not the first applicable pane in registry order. No shipped pane currently implements it.
mintClass: NamedNode and mintNew(context, options): Promise
Make the pane creatable from the Add bar. See .
predicates, classes: { [uri]: number }
Declared in the type. register indexes predicates into paneForPredicate and ignores classes; no current code in solid-panes, solid-ui or mashlib reads either index. Only the internal pane declares them.
requireQueryButton: boolean
Set by register's second argument and read by the outliner to show the query control. register assigns it unconditionally, so a value set on the pane object is overwritten with undefined when, as in the stock build, register is called with one argument.

The context

The outliner passes the same context object, of type DataBrowserContext [[PANE-REGISTRY]], to label and render. A few legacy callers inside panes pass other things.

{
  dom:     HTMLDocument,              // the document to create elements in
  session: {
    store:        LiveStore,          // the shared rdflib store, with fetcher and updater
    logic:        SolidLogic,         // solid-logic: authn, profile, containers, type indexes
    paneRegistry: PaneRegistry        // the registry this pane was registered in
  },
  environment?: {                     // set by the host: mashlib 3.0 does, plain solid-panes does not
    layout: 'desktop' | 'mobile', layoutPreference, inputMode, theme: 'light' | 'dark',
    viewport: { width, height }
  },
  getOutliner: (dom) => OutlineManager   // marked "@@ TODO Remove" in the type; the folder pane still uses it
}

Panes written for the outliner use context.dom and context.session.store. Many shipped panes also import the store singleton from solid-logic directly; it is the same store.

A minimal pane

import { Namespace } from 'rdflib'
import type { PaneDefinition } from 'pane-registry'
import * as UI from 'solid-ui'
const ns = UI.ns
const EX = Namespace('http://example.org/')

const greetingPane: PaneDefinition = {
  name: 'greeting',
  icon: UI.icons.iconBase + 'noun_339237.svg',   // any icon URL

  label (subject, context) {
    const store = context.session.store
    return store.holds(subject, ns.rdf('type'), EX('Greeting')) ? 'Greeting' : null
  },

  render (subject, context) {
    const { dom, session: { store } } = context
    const div = dom.createElement('div')
    const message = store.any(subject, EX('message'))
    div.textContent = message ? message.value : 'No message'
    return div
  }
}
export default greetingPane

How SolidOS chooses a pane

Given a subject, the outliner proceeds as follows (getRelevantPanes and getPane in solid-panes/src/outline/manager.js):

  1. If the subject is a container (its URL ends in /) and the store does not yet hold its ldp:contains listing, fetch the container as Turtle and load it.
  2. Call label(subject, context) on every registered pane, in registration order. Keep those whose label is truthy, excluding panes marked global and the pane named sharing. These are the relevant panes.
  3. If there are none, use the internal pane, which displays the raw data of any subject. With the stock registration this branch is unreachable, because the internal pane's own label is always truthy.
  4. Filter the relevant panes by audience against the user's roles. If the filter removes everything, keep the first relevant pane anyway. If the first relevant pane was registered before the first pane that passed the filter, put it back at the front, so the most relevant view is always offered.
  5. The pane shown first is the first of these that answers shouldGetFocus(subject) true, otherwise the first in the list. The rest become tabs.
  6. Call the chosen pane's render. If it throws synchronously, a panel showing the exception is rendered in its place. A render that returns nothing, or a rejected promise, is not caught.

The outliner can also be told which pane to use: an alt-click forces the internal pane, and callers may pass a required pane or a hidden list, bypassing steps 2 to 5.

Because step 2 is first-match in registration order, the order in registerPanes.js is part of the behaviour: a specific pane is registered before the general pane that would also claim its subject. The data-content, source and default panes are 27th, 28th and 33rd of 36 for this reason.

Registration

The registry is the module pane-registry. register(pane, requireQueryButton?) sets requireQueryButton on the pane, then logs and returns without registering if the pane has no name or no label; otherwise it appends the pane to list, indexes it under its name if that name is free, under its icon if it has one, and under each key of predicates. It does not throw and returns nothing, so a caller cannot tell a refused pane from an accepted one except by the console. byName(name) scans the list and returns the first match, or warns and returns null.

In the stock build the whole set is registered when solid-panes is imported: its entry point calls registerPanes(register), which imports each pane and registers it in a fixed order with the comment "earliest panes have priority". 37 calls are present, one of them conditional on an export that does not exist, so 36 panes are registered; about fifteen more are present but commented out. register is exported from solid-panes, so a host can register further panes at runtime without editing the file.

Loading panes dynamically

Everything else in this document describes what SolidOS does today. This section does not. SolidOS as released registers its panes when it is built () and has no mechanism for loading a pane named in a user's data. What follows is a sketch of one, written down so that it can be discussed and corrected. Nothing here is implemented in SolidOS, and the terms in the data examples are illustrative.

Background

The wish is old. The pane-registry README, as quoted in [[PANE-REGISTRY-28]], hopes for panes loaded according to user configuration preferences, and two open issues ask for it: one from 2019 proposing panes that are added from outside the bundle and described in RDF [[SOLID-PANES-103]], and one from 2023 describing a working but awkward way to register a pane from a page in the user's pod [[PANE-REGISTRY-28]].

At the SolidOS team meeting of 11 November 2026 it was raised again as a goal [[SOLIDOS-MINUTES-2026-11-11]]. The outline recorded there is: load a pane's JavaScript from the web; describe the pane in a small data file that points to its icon and its code; keep the list of panes a person uses in their profile; choose a pane by RDF class; have the loader call the existing register; and deal with trust once loading works. The rest of this section follows that outline.

A pane as a module

A dynamically loaded pane is an ES module at a URL whose default export is a pane as defined in : the same four members, the same optional members, the same context. Nothing about the pane itself changes; only how it reaches the registry. The example in is already in this form.

One constraint follows from loading outside the build. A pane compiled into SolidOS shares the application's single store, session and UI library. A module fetched at run time does not get them by importing its own copies: a second copy of solid-logic has a second, empty store and no login. A dynamically loaded pane therefore takes what it needs from the context it is handed (context.session.store, context.session.logic, context.dom) and does not bundle rdflib, solid-logic or solid-ui. In the current mashlib source the shared instances are also set as page globals ($rdf, SolidLogic, and the solid-panes module as panes), which is what makes a call to panes.register from a loaded script possible at all.

Describing a pane

So that SolidOS can decide whether to load a pane without running it, and so that a person can see what they are being offered, a pane has a description as data. The minimum is a name, the module URL, an icon, and the classes the pane is meant for:

@prefix ex: <https://example.org/pane#> .      # illustrative terms, not a published vocabulary
@prefix schema: <http://schema.org/> .
@prefix foaf: <http://xmlns.com/foaf/0.1/> .

<#this> a ex:Pane ;
    ex:name "quiz" ;
    ex:module <quiz-pane.js> ;
    ex:icon <quiz.svg> ;
    ex:forClass schema:Quiz ;
    schema:description "Shows a quiz and records the answers in the pod." ;
    foaf:maker <https://alice.example/profile/card#me> .

The class list is a hint for the loader, not the test. Whether a pane applies to a subject is still decided by its label, as in ; a pane loaded for schema:Quiz that returns null for a given quiz is simply not offered.

A person's list of panes

The panes a person has chosen are listed in their own data, so that the choice follows them from one SolidOS installation to another. The preferences file is the natural home: it is already where SolidOS keeps per-user settings such as workspaces (), and unlike the public profile it is private by default.

@prefix ex: <https://example.org/pane#> .      # illustrative

</profile/card#me> ex:usesPane
    <https://alice.example/public/panes/quiz.ttl#this> ,
    <https://bob.example/panes/recipe.ttl#this> .

Loading and registering

After login, once the preferences file has been read:

  1. Read the person's list of panes.
  2. For each, fetch its description. Skip it if the description cannot be read or has no module.
  3. Import the module. Skip it if the import fails or the default export has no name, label or render.
  4. Call register with the pane.
  5. Refresh the view of the current subject, since the set of relevant panes may have changed.
// Sketch only. `descriptions` is the list read from the preferences file,
// already reduced to { name, module } pairs.
async function loadPanes (descriptions, register) {
  for (const d of descriptions) {
    try {
      const pane = (await import(d.module)).default
      if (pane && pane.name && typeof pane.label === 'function' &&
          typeof pane.render === 'function') {
        register(pane)
      } else {
        console.warn('Not a pane, skipped: ' + d.module)
      }
    } catch (err) {
      console.warn('Pane failed to load, skipped: ' + d.module, err)
    }
  }
}

A pane that fails at any step is skipped and the rest continue; a broken or unreachable pane must never stop SolidOS from starting. This mirrors how register already treats a pane with no name or label ().

Order matters, and it works against a loaded pane. register appends, and selection is first match in registration order (), so a pane registered after the 36 built-in ones is offered as a tab but is never the first view for a subject that a built-in pane also claims, unless it implements shouldGetFocus. The workaround reported in [[PANE-REGISTRY-28]] is to put the pane at the front of the registry's list by hand. A real mechanism needs a deliberate rule here; see .

Security considerations

A pane is not sandboxed. A loaded module runs in the same page as SolidOS, with the logged-in session: it can read and write whatever the person can, on every pod they have access to, and it can change what the page shows. Adding a pane is therefore an act of trust comparable to installing a browser extension, and the list in is as sensitive as a password: anyone who can write to it can run code as that person.

The meeting set trust aside until loading works, and so does this sketch, but three consequences are already clear. The list must live in a document only its owner can write. SolidOS should show what it is about to load, and from where, before the first load of a pane, not after. And a pane's description should say who made it, so that a person, and later a rating or signing scheme such as the one proposed in [[SOLID-PANES-103]], has something to judge.

Open questions

  • Vocabulary: which terms describe a pane and a person's list of panes, and in which namespace?
  • Location: the preferences file, as proposed here, the profile, as recorded in the minutes, or the type index, which already maps classes to places?
  • Precedence: may a loaded pane come before a built-in pane for the same subject, and who decides: the pane, its description, or the person?
  • Timing: load every listed pane at start-up, or load a pane the first time a subject of one of its classes is shown?
  • Versions: how does a pane say which version of the context it was written for, and what happens when SolidOS moves on?
  • Other contracts: a simpler module contract, with canHandle in place of label and a registry indexed by type, is described in [[SOLID-PANES-SPEC]]. Could one loader accept both?

Creating new things

A pane that can make a new instance of what it displays, a new chat, address book or tracker, provides mintClass, the RDF class of the thing it creates, and mintNew. The Add bar in solid-ui (src/create/create.ts) lists every registered pane that has mintNew and passes the audience filter; choosing one decides where the thing goes and then calls the pane.

Where depends on how the Add bar was opened. Inside the folder pane, the pane passes the current folder: the user is asked for a name, and the new base is folder/name/; no workspace is involved. From the home pane, no folder is passed and a workspace is chosen [[WORKSPACES]]. A workspace is a container the user's preferences file points to with space:workspace, each with a space:uriPrefix. The chooser lists the user's workspaces (master workspaces excluded) and a URL field; with one workspace it is pre-selected, with several the user picks, and with none the user's storage roots are offered as candidates; in every case the user confirms, and "Make a new workspace" is offered, which writes exactly two triples, me space:workspace ws and ws space:uriPrefix prefix, into the preferences file. The new base is then the prefix plus the pane's application path segment plus a timestamped id segment.

mintNew(context, options) receives, among other things, options.newBase, options.folder (null on the workspace path), options.dom, options.div, options.me, options.noun and options.refreshTarget. It creates the initial resources, sets options.newInstance to the URL of the created subject, and resolves to the options object; the create flow throws if newInstance is missing and reads folder, newBase and refreshTarget off the resolved value. What follows is not navigation: on the folder path, an ldp:contains triple is added to the store and the folder listing refreshed; otherwise a line "Your new X is ready to be set up" with a link to it is appended. Sharon's notes [[CREATE-A-PANE]] add that a sound mintNew validates its inputs and settles the title either from the folder name or as an editable default.

Writing a pane: the practical guide

This section condenses [[CREATE-A-PANE]], Sharon Stratsianis's working notes. Where a step or rule is the editor's rather than hers, it is marked.

Steps

  1. Write label first. Decide from the subject's type in context.session.store; return null for everything else; keep it cheap, it runs for every pane.
  2. Write render. Create the root element from context.dom; read and write through the store; keep state in your components or in the RDF, not in options, which may be absent; handle a null subject if your pane can be called that way.
  3. If the pane creates things, add mintClass and mintNew; see .
  4. Import the pane in registerPanes.js and call register at the right place in the order: before any general pane that would also claim your subject.
  5. Editor's addition: start from an existing pane of similar shape, and run SolidOS locally with npm start in solid-panes to open a subject of your type.

Rules that keep panes working together

  • Keep label cheap; it can be called for several registered panes.
  • Use context.dom, not the global document; use context.session.store for RDF reads and writes.
  • Treat options as optional and per call; read only the values your pane defines. Some callers omit it; a few special-purpose panes receive a null subject.
  • Return one root element from render.
  • Register specific before general; earlier panes win when several can render the same subject.

Data, vocabularies and prefixes

A pane writes full IRIs; prefixes are only Turtle shorthand. The common namespaces come from solid-ui's ns helper (ns.rdf, ns.dct, ns.foaf, ns.ldp, and so on), which wraps solid-namespace. Prefer an existing vocabulary term whose meaning matches before inventing one; when a new term is genuinely needed, define it narrowly, document it and publish it at a stable IRI. If serialised Turtle should use a particular prefix for a namespace rdflib does not know, register it with store.setPrefixForURI(prefix, namespace); otherwise rdflib guesses a short prefix, which is only a readability issue.

UI: web components and icons

SolidOS leans heavily on custom elements. solid-ui and solid-panes provide reusable ones (providers, dialogs, buttons, headers, form controls, resource actions); check those before writing new. New components are Lit classes decorated with solid-ui's @customElement, named with the pane as prefix (reminder-pane-provider, reminder-pane-create-header), and imported somewhere that runs during pane setup so they register. For a pane built as its own package with Lit components, her questionnaire pane needed two build settings so the components survive bundling: "sideEffects": ["**/*.css", "src/components/**/*.ts"] in package.json, and the components' paths in the toolkit's litDecoratorPaths so decorators are transpiled for consumers. Inside components, Lucide is a common icon choice via unplugin-icons (import '~icons/lucide/pencil', then <lucide-pencil>), themed through CSS color; the pane's own package must declare the icon dependency. The pane's icon member itself is a URL, in shipped panes one of solid-ui's noun_*.svg files.

Conformance

This document describes running code and legislates nothing beyond it. The registry checks only that a pane has a name and a label; every other statement about a pane above describes what the outliner and the stock panes assume or do. A conforming pane for the purposes of this document is a PaneDefinition with a name, an icon, a label that returns a truthy string or null, and a render that returns one element. A conforming host registers panes through the registry, selects as in unless explicitly directed to a pane, and calls render with a context as in .
