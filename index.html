SolidOS is a data browser for Solid pods. It shows any resource on a pod through panes: small, self-contained views that each know how to display one kind of thing. This document describes how SolidOS is put together, what a pane is, how SolidOS decides which pane to show, how panes are registered, and how a pane creates new things. It is written down from the running code and from the SolidOS team's own notes, so that a pane written from this document behaves like the panes SolidOS ships.

This is a first draft. It documents SolidOS as it is in November 2026 (mashlib 3.x, solid-panes 4.x, pane-registry 2.x). Where this document and the code disagree, the code is right and this document has a bug; please file an issue.

Introduction

A Solid pod holds a person's data as web resources: RDF documents, folders (containers), images, PDFs, anything with a URL [[SOLID-PROTOCOL]]. SolidOS is the application that lets a person browse and edit those resources without a separate app for each kind of data. Point it at a URL and it shows the thing at that URL in the most suitable view it has.

The views are called panes. A pane for address books shows an address book; a pane for chats shows a chat; a pane for folders shows a file listing; a pane for RDF source shows the triples. SolidOS ships about fifty of them. When several panes could show the same resource, SolidOS shows the best one first and offers the others as tabs.

This document has two audiences: someone who wants to understand what SolidOS does when it opens a URL, and someone who wants to write a pane. Sections 3 to 7 are the description. Section 8 is the practical guide, drawn from [[CREATE-A-PANE]].

Terminology

subject
The RDF resource being displayed, identified by a URL and represented in code as an rdflib NamedNode [[RDFLIB]]. A subject may be a document, a thing inside a document (a URL with a fragment), or a container.
store
The in-memory RDF graph that SolidOS loads documents into and writes changes through. There is one store per page, shared by all panes.
pane
A JavaScript object that can say whether it applies to a subject and, if so, render it. Defined in .
pane registry
The ordered list of panes known to the page, with lookup by name, icon and predicate. Provided by the pane-registry package [[PANE-REGISTRY]].
outliner
The part of SolidOS that takes a subject, asks the registry which panes apply, and places the chosen pane on the page. Lives in solid-panes/src/outline/.
context
The object handed to every pane call, carrying the document, the session and the store. Defined in .
workspace
A container on the pod, named in the user's preferences file, where a pane creates new things. See .

How SolidOS is put together

SolidOS is a set of npm packages assembled into one browser bundle. Reading from the bottom up:

PackageRole
rdflib [[RDFLIB]]The RDF store, the fetcher that loads documents into it, and the updater that writes changes back with PATCH.
solid-logic [[SOLID-LOGIC]]Authentication, the shared store instance, and the business logic that is not UI: profiles, type indexes, containers, access control helpers.
solid-ui [[SOLID-UI]]Widgets and web components panes build from: forms, tables, login, the sharing dialog, the create ("Add") bar, styles.
pane-registry [[PANE-REGISTRY]]The PaneDefinition type and the registry: register, list, byName, paneForIcon, paneForPredicate.
solid-panes [[SOLID-PANES]]The panes themselves, the outliner that places them, and registerPanes.js, the ordered list that registers them. Some panes live in their own repositories (profile, contacts, chat, folder, issue, meeting, source, markdown) and are pulled in here.
mashlib [[MASHLIB]]The bundle a pod serves as its data browser: solid-panes plus the page chrome. A pod that serves browse.html or embeds mashlib shows SolidOS for every resource.

Opening a URL goes like this. mashlib starts, solid-panes calls registerPanes() so the registry is full, and the outliner is created with a context. The outliner takes the subject from the page URL, makes sure its document is in the store (loading it if needed; for a container it also loads the container listing), asks every registered pane whether it applies, picks one, calls its render, and puts the returned element on the page under a row of tabs for the other applicable panes.

The pane

A pane is a JavaScript object conforming to PaneDefinition [[PANE-REGISTRY]]. Three members are required; the rest are optional.

Required members

name: string
A short identifier, unique within the registry, used by byName and in log output. Examples: "contacts", "folder", "source".
icon: string
The URL of an icon image shown on the pane's tab. The registry also indexes panes by icon.
label(subject, context): string | null

Decides whether the pane applies to the subject, and names it if so. The function MUST return a non-empty string when the pane can display the subject, and null when it cannot. The string is used as the tooltip and tab label.

A label function MUST be synchronous and SHOULD be cheap: the outliner calls it on every registered pane for every subject shown. It SHOULD decide from what is already in context.session.store, typically the subject's rdf:type, and SHOULD NOT start network requests.

render(subject, context, options?): HTMLElement

Builds the view. It MUST return a single element, created with context.dom rather than the global document, which the outliner inserts into the page. The pane owns everything inside that element and nothing outside it.

Reads and writes go through the store: read with the store's query methods, write with its updater, so that changes reach the pod and other panes see them. options is per-call and MAY be absent; a pane MUST NOT treat it as persistent state and MUST render sensibly without it. A few internal callers invoke render with a null subject for panes that do not show a subject (the home pane, for instance); a pane that can be called that way documents it.

Optional members

global: boolean
A pane that is about the session rather than any subject, such as the home pane or preferences. Global panes are never offered as tabs for a subject.
audience: NamedNode[]
Roles the user must have for the pane to be offered, for example a developer role for the source pane. See .
shouldGetFocus(subject): boolean
Lets a pane claim the first tab even when it is not the first applicable pane in registry order.
mintClass: NamedNode and mintNew(context, options): Promise
Make the pane creatable from the Add bar. See .
predicates, classes: { [uri]: number }
Hints that index the pane by predicate or class in the registry, used by some navigation widgets.
requireQueryButton: boolean
Set by register's second argument; asks for the query control to be shown with the pane.

The context

Every label and render call receives the same context object, of type DataBrowserContext [[PANE-REGISTRY]]:

{
  dom:     HTMLDocument,              // the document to create elements in
  session: {
    store:        LiveStore,          // the shared rdflib store, with fetcher and updater
    logic:        SolidLogic,         // solid-logic: authn, profile, containers, type indexes
    paneRegistry: PaneRegistry        // the registry this pane was registered in
  },
  environment?: {                     // present in newer builds
    layout: 'desktop' | 'mobile', layoutPreference, inputMode, theme: 'light' | 'dark',
    viewport: { width, height }
  },
  getOutliner: (dom) => OutlineManager   // deprecated; will be removed
}

A pane MUST use context.dom and context.session.store and SHOULD NOT reach for module-level singletons, so that the same pane code works wherever the outliner is embedded.

A minimal pane

import { Namespace } from 'rdflib'
import { PaneDefinition } from 'pane-registry'
import * as UI from 'solid-ui'
const ns = UI.ns
const EX = Namespace('http://example.org/')

const greetingPane: PaneDefinition = {
  name: 'greeting',
  icon: UI.icons.iconBase + 'noun_339237.svg',

  label (subject, context) {
    const store = context.session.store
    return store.holds(subject, ns.rdf('type'), EX('Greeting')) ? 'Greeting' : null
  },

  render (subject, context) {
    const { dom, session: { store } } = context
    const div = dom.createElement('div')
    const message = store.any(subject, EX('message'))
    div.textContent = message ? message.value : 'No message'
    return div
  }
}
export default greetingPane

How SolidOS chooses a pane

Given a subject, the outliner proceeds as follows (getRelevantPanes and getPane in solid-panes/src/outline/manager.js):

  1. If the subject is a container (its URL ends in /), load the container listing into the store first.
  2. Take every registered pane, in registration order, whose label(subject, context) returns a non-null value, excluding panes marked global and the sharing pane. These are the relevant panes.
  3. If there are none, show the internal pane, which displays the raw data of any subject.
  4. Filter the relevant panes by audience against the user's roles. If the filter removes everything, keep the first relevant pane anyway. If the first relevant pane was registered before the first pane that passed the filter, put it back at the front, so the most relevant view is always offered.
  5. The pane shown first is the first of these that answers shouldGetFocus(subject) true, otherwise the first in the list. The rest become tabs.
  6. Call the chosen pane's render. If it throws, a panel showing the exception is rendered in its place, so a broken pane never blanks the page.

Because step 2 is first-match in registration order, the order in registerPanes.js is part of the behaviour: a specific pane is registered before the general pane that would also claim its subject. The source, data content and default panes are registered near the end for this reason.

Registration

The registry is the module pane-registry. register(pane, requireQueryButton?) appends the pane to list, indexes it under its name, its icon and each key of its predicates, and refuses a pane that has no name or no label. byName(name) finds a pane; list is the ordered array the outliner iterates.

In SolidOS the whole set is registered once, at startup, by registerPanes() in solid-panes/src/registerPanes.js, which imports each pane and calls register in a fixed order. A pane that is not in that file is not part of the build and will not be offered; see for how a new pane is added.

Creating new things

A pane that can make a new instance of what it displays, a new chat, address book or tracker, provides mintClass, the RDF class of the thing it creates, and mintNew. The Add bar in solid-ui (src/create/create.ts) lists every registered pane that has mintNew; choosing one asks where to create it and then calls the pane.

Where is a workspace [[WORKSPACES]]: a container on the pod that the user's preferences file points to with space:workspace, each with a space:uriPrefix that becomes the base for new URLs. With one workspace it is used silently; with several the user chooses; with none the user is asked for a folder or offered to create a workspace, which writes those two triples. If the user navigated from a folder, that folder is used and no workspace is asked for.

mintNew(context, options) receives options.newBase, the URL the new thing should live under, and options.folder. It MUST create the initial resources (documents, and containers if needed), set options.newInstance to the URL of the created subject, and resolve to the options. SolidOS then navigates to newInstance, where the same pane's label will claim it. A sound mintNew validates its inputs, derives or sets an initial title, and does nothing the user did not ask for.

Writing a pane: the practical guide

This section condenses [[CREATE-A-PANE]], the SolidOS team's working notes, into the steps and rules that matter.

Steps

  1. Start from an existing pane of similar shape. A pane is one directory in solid-panes/src/ or its own package depending on solid-ui and solid-logic.
  2. Write label first. Decide from the subject's type in the store; return null for everything else.
  3. Write render. Create the root element from context.dom; read and write through the store; keep state in your components or in the RDF, never in options.
  4. If the pane creates things, add mintClass and mintNew.
  5. Import the pane in registerPanes.js and call register at the right place in the order: before any general pane that would also claim your subject.
  6. Run SolidOS locally (npm run dev in solid-panes or the mashlib dev server) and open a subject of your type.

Rules that keep panes working together

  • Keep label cheap and synchronous. It runs for every pane on every navigation.
  • Use context.dom, never the global document; use context.session.store, never your own fetch, for pod data.
  • Treat options as optional and per-call. Some callers omit it; some special panes are called with a null subject.
  • Return exactly one root element from render.
  • Register specific before general.

Data, vocabularies and prefixes

A pane writes full IRIs; prefixes are only Turtle shorthand. The common namespaces come from solid-ui's ns helper (ns.rdf, ns.dct, ns.foaf, ns.ldp, and so on). Prefer an existing vocabulary term whose meaning matches before inventing one; when a new term is genuinely needed, define it narrowly, document it and publish it at a stable IRI. If a serialised Turtle document should use a particular prefix for a namespace rdflib does not know, register it with store.setPrefixForURI(prefix, namespace); otherwise rdflib invents a short prefix, which is only a readability issue.

UI: web components and icons

SolidOS UI is built from custom elements. solid-ui and solid-panes provide reusable ones (providers, dialogs, buttons, headers, form controls, resource actions); reuse before writing new. New components are Lit classes decorated with solid-ui's @customElement, named with the pane as prefix (reminder-pane-header), and imported somewhere that runs during pane setup so they register. Two build settings keep them alive in the bundle: mark component files as side-effectful in package.json ("sideEffects": ["**/*.css", "src/components/**/*.ts"]) and list their paths in the toolkit's litDecoratorPaths so decorators are transpiled for consumers. Icons inside panes commonly come from Lucide via unplugin-icons (import '~icons/lucide/pencil', then <lucide-pencil>), themed through CSS color; the pane's own package must declare the icon dependency.

Conformance

A conforming pane is a PaneDefinition with a name, an icon, a label that returns a non-empty string or null without network access, and a render that returns one element created from context.dom. A conforming host registers panes through the registry, selects as in , and calls render with a context as in .
